# DECISIONS.md — why we built it this way
> Append‑only. One dated entry per meaningful decision: what we chose, what we rejected, and **why** (the trade‑off). Never rewrite past entries. **No secrets** (no keys, passwords, tokens) — reasoning only. The "checkpoint matterchat" command appends here.

### 2026-07-30 — Firm-scoped ROOM enumeration: rooms keep a legacy-global cohort (branch feat/room-firm-scoping)
**Chose:** stamp `customFields.firmId` on rooms at creation (beforeCreateRoom hook: discussion parent > containing team > creator; forged inbound firmIds deleted) and scope every public-room enumeration surface (spotlight rooms + team mentions, /v1/directory channels+teams, channels.list, deprecated DDP channelsList/browseChannels/spotlight, teams.autocomplete) to "caller's firm OR rooms with NO firmId", with the caller's own subscriptions always visible and admins/feature-off a total no-op. Room cohort semantics deliberately DIFFER from the user directory (#166, where a firm member sees ONLY their firm): unstamped rooms stay visible to everyone because they are legacy/workspace-wide by definition and hiding them would break every pre-firms workspace room overnight. Backfilled via migration v340 (same priority order, idempotent, $exists-guarded) because Firms_SelfServe_Enabled is ALREADY live on prod with public registration — firm-created rooms exist today and "legacy stays global" alone would leave them enumerable cross-firm forever. Non-admins can no longer strip/forge the stamp through saveRoomSettings roomCustomFields (wholesale-replace guard); an admin CAN un-stamp a room to deliberately make it workspace-wide. Model layer: additive optional `extraQueries` ($and-composed) on 4 room finders + a sparse `customFields.firmId` index in modelIndexes (fresh installs skip old migrations, so the index cannot live only in v340).
**Rejected:** (a) reusing getFirmScopeExtraQuery verbatim for rooms — its unstamped-cohort arm would hide all legacy rooms from firm users; (b) post-filtering query results instead of pushing the scope into Mongo — the limit-5/paginated lists would return short or empty pages while matches exist; (c) stamping the firm home team room in the creation hook — impossible, createFirm writes the owner's firmId only AFTER Team.create returns, so createFirm stamps that room itself; (d) folding the canAccessRoom probe-surface backstop into this change — it alters JOIN semantics (see open follow-up below).
**Why:** enumeration was the widest remaining shared-workspace leak class after #166 (any user could list every firm's public channels and teams by name), and prod exposure is live now. Scope is DISCOVERY-only by design: membership always wins (subscription arms in every query), so nobody loses access to a room they are in.
**Open follow-up (founder decision):** public rooms remain probeable/joinable/readable cross-firm by EXACT name or id (channels.info/join/history, rooms.nameExists, getRoomByTypeAndName, teams.listRooms of a known public team). The architectural backstop is a firm gate in the public-room validators of server/services/authorization/canAccessRoom.ts (subscribed members keep access via _validateIfAlreadyJoined, but roomAccessAttributes must gain customFields) — that changes join semantics for workspace-wide rooms too, so it is phase 2, not silently folded in here.

### 2026-07-30 — Remove the Rocket.Chat EE tree entirely: pure-MIT fork (PR #168)
**Chose:** delete both Enterprise-licensed trees (`apps/meteor/ee/`, `ee/`) and re-provide the load-bearing pieces as clean-room MIT: a full presence service (`packages/presence` — the EE tree was the ONLY thing that ever marked users online), a permanent community-edition license service (`packages/license`, same npm name so all import sites resolve unchanged), a dormant media-calls stub, the read-receipts archive model+cron, 7 settings MIT code reads that only EE declared, and MIT licenses routes. Staged as: replacements built additively → boot flip → deletion → config cleanup, per the audited plan in `docs/design/MATTERCHAT-EE-REMOVAL-PLAN.md` (5 mappers + planner + adversarial critic; the critic's two blockers — duplicate workspace name, VideoConf/Calendar settings gap — were fixed before execution).
**Rejected:** (a) registering the workspace with Rocket.Chat Cloud to stop the air-gapped countdown — stops the clock but keeps the license machinery, the phone-home dependency, and the EE-licensed code shipping in a commercial fork; (b) patching the air-gap enforcement in place — modifying EE-licensed code to defeat its own license check is legally murky, whereas NOT SHIPPING that code at all is exactly what its license contemplates; (c) `scripts/fossify.ts` — deletes the trees but leaves dangling imports (non-building repo); (d) buying the EE scalability license for multi-pod — Path B makes it unnecessary (one firm per instance = small singleton workloads).
**Why:** the fork was ~9 days from Rocket.Chat's unregistered-workspace read-only mode, could never run >1 pod (cross-pod fan-out gated on a paid module — proven by live DDP test 2026-07-23), and the product is meant to be mostly free — a permanent dependency on a competitor's licensing was untenable. The audit confirmed MatterChat's own features (Chi, Boards, firms, omnisai-oauth) had ZERO imports from ee/, so the fork's own value was never entangled. Losses are all unused (marketplace apps, omnichannel premium, ABAC, device mgmt, Matrix federation, microservices mode — founder confirmed each).

### 2026-07-30 — Multi-org architecture: one instance per firm (Path B), shared-workspace firms demoted to trial tier
**Chose:** each customer org ultimately gets its own MatterChat instance at `<firm>.matterchat.com` (ApplicationSet + Helm factory in MatterChat-New, CentralizedAuth org-picker for post-login routing), because for LAW FIRMS data isolation is a sales/compliance requirement a shared Rocket.Chat workspace cannot honestly meet: the audit found firm "isolation" covered only 3 enumeration surfaces while autocomplete/users.info/presence/DMs/public-rooms all leaked, and the feature's own docs call it "a privacy measure, not an isolation guarantee". Per-instance also matches everything already built (cross-firm CFCS assumes one firm per instance; CasePro wiring is per-instance; first-admin bootstrap and the org-switcher stub only make sense per-instance) and erases the EE scalability-license need. Interim: closed the five worst shared-workspace leaks anyway (PR #166) because self-serve firms is LIVE on prod with public registration.
**Rejected:** hardening the shared workspace into real tenancy — the fork's own spike prices it at 800–1000h with residual leak risk, and every upstream merge re-opens the audit; per-firm URLs via in-instance host routing — Rocket.Chat is architecturally one-workspace-per-deployment.
**Why sequenced behind Mongo auth:** the cluster Mongo has NO auth and a shared oplog, so per-firm databases today give namespacing, not isolation — a compromised firm pod could read every firm's data. Auth + per-firm users is the floor before customer #2; separate replica sets are the contractual-isolation upgrade path.

### 2026-07-17 — CasePro sync reads must page fully (50-row cap bug)
**Chose:** dedicated `listAllMatters()` / `listAllIntakes()` on the CasePro client (full pagination via `queryAll`, 200/page) and pointed the bulk consumers at them: `seedFromCasePro` (was silently seeding only the FIRST 50 matters — the transport default) and the leads `pullFromCasePro` (was capped at 500 intakes).
**Rejected:** raising the `listMatters` default limit — the paged default is correct for the browse/list REST endpoints; only bulk sync should fetch everything. `MAX_MATTERS_SCANNED=200` in `mattersSnapshotMemo` left alone on purpose: it is a cost cap on a per-matter snapshot fan-out, not a sync completeness bug.
**Why:** orgs with >50 matters lost the rest of their caseload on seed; the returned `total` was never used to page.

### 2026-07-02 — Boards two-way calendar sync + email-to-task: reuse connector OAuth/crypto, new decoupled store, dark by default
**Chose:** build Phase-3 two-way calendar sync (Google Calendar + Outlook/Graph) + email-to-task as a **provider-pluggable subsystem** under `server/lib/boards/calendar-sync/`, mirroring the external-workspace connector architecture instead of extending it. Token storage REUSES the connector `tokenCrypto` (AES-256-GCM, env `EXTERNAL_TOKEN_ENC_KEY`) — **no new crypto** — but on a SEPARATE per-user store `boards_calendar_connections` (unique `{userId,provider}`), keeping calendar concerns out of the chat-oriented `external_workspace_connections` (which carries `bridgedChannels`). OAuth is a clean-room clone of the proven connector PKCE dance (`/_google` + `/_teams` routes): server-owned redirect, PKCE S256, state parked in `CredentialTokens`, one-time HttpOnly state cookie, `serverFetch` token exchange, `ignoreSsrfValidation:true` for the FIXED Google/Microsoft hosts only. Outbound = a third fan-out on `emitBoardEvent` (same fire-and-forget + dynamic-import + swallowed-catch discipline as the CasePro task-sync fan-out) → `eventFanout` pushes a due-dated card to its assignees' connected calendars; correlation stored on the card as `calendarSync[]` (external event id + etag + lastPushedDueDate, the tasksync external_ref pattern). Inbound = a 15-min cron (`BoardsCalendarSync`) that PUSHes + POLLs each connected connection via Google `syncToken` / Graph `deltaLink` cursors: a moved event updates the mirrored card's due date; a brand-new event becomes a card ONLY on an opt-in `inboundBoardId`. Email-to-task = a fail-closed HMAC webhook receiver `POST /_boards_email/inbound` (cloned from `/_casepro/webhook`: env/setting secret, `sha256=` constant-time verify, 202-drop-and-never-leak, 2 MB cap, ack-then-setImmediate) routed by a plus-addressed capability token (`boards+<token>@`, 43-char `Random.secret`) resolving to a board's opt-in `emailIntake` → `createCard` AS the intake owner (the forms public-submit precedent). We do NOT run a mail server — a provider (SES inbound / forwarder) POSTs the parsed mail. Everything GATED off by default: `Boards_Calendar_Sync_Enabled` / `Boards_Email_To_Task_Enabled`; per-provider `is*Configured()` also needs a client secret; no creds ⇒ connect returns `configured:false`, jobs no-op, ZERO external traffic. **Rejected:** (a) extending `external_workspace_connections` — its `bridgedChannels` fan-out and chat `ExternalProvider` union don't fit calendars; a separate store keeps blast radius low; (b) a new crypto key (`CALENDAR_SYNC_TOKEN_ENC_KEY` the survey suggested) — reusing `EXTERNAL_TOKEN_ENC_KEY`/`tokenCrypto` is the mandate and one fewer secret to provision; (c) reflecting a calendar-side event DELETE as a due-date wipe — a deleted mirror event must never silently unschedule a legal deadline (inbound cancel is ignored for due dates); (d) Graph change-notification/Google push webhooks for inbound this milestone — polling ships now, push subscriptions are the connector-parity follow-up. **Why / needs live verification:** all provider HTTP is clean-room from public docs; the Google Calendar v3 + Graph `/me/events` + `calendarView/delta` shapes and the token-exchange/refresh envelopes must be verified against real accounts on first connect. Firm must provision: a **Google Cloud OAuth client** (Web app; scope `calendar.events`; redirect `<site>/_boards_calendar/google/oauth/callback`) and an **Entra app** (reuse the Teams app + add `Calendars.ReadWrite`; redirect `<site>/_boards_calendar/outlook/oauth/callback`), pasted into the `Boards_Calendar_*` settings; `EXTERNAL_TOKEN_ENC_KEY` for encryption; `BOARDS_EMAIL_WEBHOOK_SECRET` for email intake. Touched `packages/{core-typings,model-typings,models}` (card `calendarSync`, board `emailIntake`, new `IBoardCalendarConnection` + model, BoardsCards calendar methods) — dist rebuilt; meteor `tsc --noEmit` = 0 errors; 37 new unit specs (mapping/parse/HMAC/token-roundtrip) + connector (73) + boards (63) suites green.

### 2026-07-02 — CasePro live wire: JSON-RPC MCP gateway transport, env-only secret, refuse-over-leak
**Chose:** the live CasePro transport speaks the deployed casepro-mcp-v2 protocol — JSON-RPC 2.0 `tools/call` POSTs to `{base}/mcp/v2` (verified live: `/mcp` and `/mcp/v2` both answer, 401 without a key; `/health` green) — NOT the bare `POST /query_entities` REST verbs the M2 skeleton guessed. Auth route A: `X-MCP-API-Key` from env `CASEPRO_MCP_API_KEY` ONLY (secrets never in Mongo settings) + `X-Organization-ID` (env `CASEPRO_ORG_ID` / setting `CasePro_Org_ID`); `CasePro_Auth_Mode` ships with a declared-but-unimplemented `keygate` value (route B seam). Misconfiguration = REFUSAL: transport=rest with no key/https-URL degrades to the stub with a loud boot warning and a `boards.casepro.status` diagnostics endpoint — never an unauthenticated live call. Killed `ignoreSsrfValidation:true`: SSRF checks ON, allow-list = exactly the configured gateway host, https only, `followRedirects:false` (a 3xx would re-send the key). The gateway paginates by `limit` only (no offset) and returns no true total, so `query()` over-fetches `offset+limit`, slices locally, and signals maybe-more through `total` for the client's accumulate loop. Writer identity: writes carry an advisory `X-Acting-User` header (gateway identity stays the service key); the acting uid threads from caseproSync/convertToMatter via an optional `CaseProCallContext`. Enforced the 4 existing-but-unchecked permissions (view on `boards.casepro.*`, sync on `syncFromCasePro`/`seedFromCasePro`, write on `convertToMatter`-when-enabled, manage on status) + migration v338 backfills partner/attorney grants ($addToSet only). New `BoardsCaseProLeadsPull` cron (15 min) reuses `pullFromCasePro`, gated on CasePro_Enabled AND a live transport AND an existing board (never creates one, never syncs stub rows). `CasePro_Web_URL` drives the matter-card "Open in CasePro" link; empty ⇒ hidden, not a dead href. **Rejected:** key-as-setting (Mongo dumps/backups leak it); keeping `ignoreSsrfValidation` (admin-editable base URL = SSRF primitive); silently serving stub when live was requested (fake data impersonating a CRM is worse than an error); per-user token exchange now (the gateway's session path exists but CentralizedAuth token plumbing isn't there — that's the KeyGate/route-B follow-up). **Why:** live writes stay pilot-scoped behind `CasePro_Enabled` + `boards-casepro-write`; response envelopes (`record`/`created`/`updated`) are parsed defensively because the local casepro-mcp-v2 checkout is stale — first run with a real provisioned key must verify them (see docs/features/casepro-integration.md).

### 2026-07-02 — /chi asks the CHI platform agent (env-configured adapter, "Chi" bot user, placeholder-edit UX) — NOT the Boards AI provider
**Chose:** wire the in-channel assistant to the **AI-Agents ("Chi") platform** through a tiny never-throw adapter (`server/lib/chi/client.ts`): `POST {CHI_API_URL}/api/v1/chat/agents/{CHI_AGENT_ID}/chat` with the one configured credential sent as BOTH `Authorization: Bearer` and `X-API-Key`, body `{ message }` = a rendered context block (channel name + the room's `matterId` + asker) + the question, answer parsed defensively across the response-field spellings. All three env vars optional — unset degrades to "CHI is not configured". UX: slash command posts a real "Chi is thinking…" message as a lazily-created `chi.bot` user and **edits it in place** with the answer (attributed footer with the matter id) or a friendly failure; validation misses are ephemeral to the caller only; the command bus never waits on the agent. Gated by a new `chi-use` permission seeded to `user` (any member) + the legal roles, so admins can tighten without a deploy. Content is never logged server-side.
**Rejected:** (a) reusing the existing Boards AI provider seam (`server/lib/boards/ai/`) — that is a direct-LLM text generator over a pre-rendered snapshot; the founder requirement is "whatever detail the user needs", which needs the CHI agent's CasePro MCP **tools** (live queries over the whole CRM), not a static snapshot; (b) posting answers via rocket.cat with an alias — a real bot user gives clean attribution, avatar, and audit; (c) blocking the slash-command callback on the agent call — agent latency is seconds, placeholder-edit keeps the channel responsive.
**Why dual-header:** the ai-agents skill (api.md) pins user auth = CentralizedAuth Bearer and S2S = `X-API-Key` (chi_api_keys), but does not pin which one the `/chat` group accepts from a service caller — sending both means whichever the deployment honors wins; the CONTRACT comment in client.ts carries the exact curl to verify live, then pin and drop the dual send. **CHI go-live is deploy-time, not new code:** (1) push `staging` in `~/matterchat-mcp-v2` (workflow deploys to `matterchat-mcp-v2.stg-omnisai.io`; secret `matterchat-mcp-v2-secrets` first); (2) register a CHI agent attached to casepro-mcp-v2 + matterchat-mcp-v2, system prompt = org-scoped legal assistant that answers ONLY from tool results for the given matter id, cites the matter id, and refuses cross-matter fishing; (3) set the three CHI_* envs via MatterChat-New (ArgoCD).

### 2026-07-01 — views.cards pages opt-in with a per-group CAP (not within-group offset); leads.list pages in Mongo
**Chose:** for `boards.views.cards` (saved views), opt-in `offset`/`count` page the flat `cards` array (standard envelope, `total` = full match count) and an opt-in `groupLimit` caps each group's cards while every group always carries its exact `total` + `hasMore`; groups keep bucketing the FULL sorted match set so per-group totals/membership stay correct whatever the flat page. No params ⇒ byte-compatible full response (groups gain only the additive total/hasMore fields). Also made the view sort a total order (`_id` tie-break, default `position`) — offset pages are only disjoint across requests under a deterministic sort, and `BoardsCards.search`'s bare `{position:1}` wasn't one. For `boards.leads.list`, the whole filter set (boardId/statusId/ownerId + the `q` haystack as per-field escaped regex + `$toString(refNo)` via `$expr`) now composes into ONE Mongo query paged by `findPaginated` (sort `capturedAt:-1,_id:-1` — the explicit sort the statusId finder already had); the historical no-params default page is now enforced by the query's `limit`, not a post-`toArray()` slice. **Rejected:** per-group offset/count for views.cards — every shipped consumer (TableView renders every card of every group; DashboardView only needs per-group counts; Timeline/Gantt take the flat set) buckets client-side and none drills into a single group, so within-group cursors would add N-queries-per-request complexity with zero consumers; cap+total serves the only prospective pattern ("first N, +K more"). Also rejected rebuilding the `q` search as a cross-field concat `$expr` — per-field match drops only the accidental "query straddles two joined fields" case. **Why:** views.cards must still scan the full filtered set server-side (JS `field:<id>`/undated-last sort + multi-membership grouping need it for exact group totals) — this bounds the RESPONSE; pushing sort+group into an aggregation is the follow-up if scan cost ever bites. NOTE: this touched `packages/rest-typings` (views.cards ajv schema + DTO) — rebuild its dist (`yarn workspace @rocket.chat/rest-typings run build`) before a meteor `tsc`/prod build.

### 2026-07-01 — Boards pagination pushed into Mongo; myDay/search page opt-in (full set stays the no-params default)
**Chose:** make the boards read helpers (`server/lib/boards/reads.ts`) page in MongoDB — `findPaginated` (skip/limit on a deterministic sort + `countDocuments` for `total`) instead of `cursor.toArray()` + in-memory slice — for boards.list / boards.cards / boards.activities; gave `boards.cards.myDay` + `boards.cards.search` the standard offset/count/total envelope but **only when the caller passes offset/count** (no params ⇒ historical behavior: full myDay set, 50-hit search cap — now enforced by the query's `limit`, not a slice). BoardView fetches cards via `useInfiniteQuery` in pages of 100 (streams pages until the board is complete) instead of one `count: 1000` request. **Rejected:** forcing the RC default page size (50) on myDay — the planner/calendar/CHI clients bucket the FULL feed client-side and would silently truncate.
**Why:** the endpoints already spoke the offset/count/total envelope but the server still materialized every card/activity row per request, so boards got slower as cards piled up; and `count: 1000` was silently capped at `API_Upper_Count_Limit` (100), truncating boards >100 cards — paging to `total` fixes that for real. No `packages/*` were touched (schemas already allowed offset/count), so there is no dist-rebuild step for this change. Known follow-up: `boards.views.cards` (saved views) still returns the full filtered set — its server-side groupBy needs a per-group paging design first.

### 2026-06-25 — STAGING IS DEPLOYED BY ARGOCD (from MatterChat-New), NOT this repo's GitHub Actions deploy
**Discovered after hours of deploying into a void.** The running staging app is owned by an **ArgoCD Application `matterchat-staging`** (namespace `argocd`, automated + prune + selfHeal) that syncs from **`OmnisAIOrg/MatterChat-New`**, path `kubernetes/staging/`. ArgoCD owns the Deployment, Service(s), and **Ingress**. The image is still built by THIS repo's GHA (push to staging → ECR `matterchat:staging-latest`), so **code** changes reach the running pod, but **manifest/env** changes in this repo's `kubernetes/staging/*.yaml` do NOT — ArgoCD reverts them.
**Chose:** make this repo's deploy pipeline **BUILD-ONLY** (PR #16) — build + push the image, then `kubectl delete pod -l app=matterchat` so the ArgoCD-managed Deployment recreates it on the new image. **Rejected:** the prior `kubectl apply -f kubernetes/staging/*` + `kubectl set image` + rollout.
**Why:** that prior approach FOUGHT ArgoCD's self-heal. The committed Ingress used group `staging-backend-shared`/order 870; applying it flipped MatterChat onto the **backend** ALB while DNS points at the **frontend** ALB (`staging-frontend-shared`/360) → public **404** on every deploy. We chased it as a "recurring outage" / "crash loop" for hours; the pod was healthy the whole time — only the ALB binding was wrong. The committed `kubernetes/staging/*.yaml` is now **dead** (ArgoCD/MatterChat-New is the source of truth). No local `kubectl`; introspect via the founder-authorized read-only `matterchat-staging-diag.yml` (`workflow_dispatch` on `develop`).

### 2026-06-25 — OmnisAI login: config in the DB (survives ArgoCD); accept id_token without iss/aud (back-channel-established)
**Chose:** seed `OmnisAI_OIDC_Issuer` + `OmnisAI_OIDC_Client_Id` as PERSISTED Mongo settings (and `getConfig` reads settings-first, env-fallback) rather than env on the Deployment. **Why:** the OIDC env only existed in the dead committed yaml; ArgoCD's manifest lacks it, so the pod never got it → `not_configured`. Mongo settings persist across pod restarts AND ArgoCD syncs (ArgoCD doesn't touch the DB) — exactly how `OmnisAI_OIDC_Enabled` already survived. Also held `Show_Setup_Wizard='completed'` via a `settings.watch` (the "create workspace" detour was RC's cloud-registration re-flipping it to `in_progress` each boot).
**Chose:** `verifyIdToken` accepts a missing `iss`/`aud`; validates host/value when present; keeps `exp`+`sub` hard. **Why:** CentralizedAuth's better-auth MCP id_token OMITS `iss` (dead-ended at `id_token_bad_issuer_got_undefined`). In the auth-code+PKCE flow the token is fetched directly from the issuer's token endpoint over TLS (bound to our state cookie + PKCE verifier) — the issuer is established by the back-channel, not a claim an attacker can set. **Still FAIL-SOFT (staging):** Ed25519 signature verify (rejects valid tokens — JWS/alg detail) + nonce. **Production bar:** fix the signature verify + have CentralizedAuth emit standard iss/aud/nonce, then re-enable strict (the claim KEYS are now logged to drive this).

### 2026-06-24 — Omnis Boards: hand-build the Gantt; do NOT adopt Plane or any third-party Gantt lib
**Chose:** build the Gantt natively in the existing Timeline view (a pure `ganttModel.ts` + a `GanttChart.tsx` renderer), reusing the card data already there (startDate/dueDate/relations/isMilestone/priority/checklists) and the generic `boards.views.cards` + `boards.cardUpdate` surface.
**Rejected:** adopting **Plane** (plane.so) wholesale — AGPL-3.0, a second un-owned Django/Postgres app with no legal concept; and dropping in a "free" Gantt library (dhtmlx/SVAR are GPL or paywall critical-path/auto-schedule).
**Why:** MatterChat's value is that it stays MIT/proprietary and sellable (on RC's MIT core); a copyleft dependency or a second app is the opposite. Hand-building keeps it standalone-safe, themed, and license-clean, and the scheduling logic (the legal moat) stays ours. Cost: we write the bars/arrows/drag ourselves — bounded.

### 2026-06-24 — Subtasks reuse the parent/child relation; resolve children per-id, not from the board-cards cache
**Chose:** subtasks are ordinary child cards linked by the existing `child` relation (the service auto-mirrors the inverse `parent` edge); the panel resolves each child by id (`useQueries` over `boards.card`).
**Rejected:** a new "subtask" entity; and deriving children from the `boards.cards` list.
**Why:** the relation primitive already existed. `boards.cards` caps at `API_Upper_Count_Limit` (100), so deriving children from it silently dropped subtasks on large boards (a multi-agent review caught this). Per-id resolution is correct at any size and — since `getCardForUser` returns archived cards too — keeps the panel count consistent with the board-tile badge.

### 2026-06-24 — Time tracking via REST routes + service fns, additive optional card fields
**Chose:** an `ITimeEntry` sub-doc + optional `timeEstimateMinutes`/`timeEntries` on `IBoardCard`; `logTime`/`deleteTimeEntry` in the shared service with new REST routes (mirroring the checklist `$push`/`$pull` pattern); the estimate rides the existing `boards.cardUpdate`. Validation at both the ajv and service layers.
**Rejected:** Meteor methods for the entry mutations (checklists/comments are REST-only in this fork — methods would be inconsistent and need extra `ServerMethods` typing); a separate time-tracking collection.
**Why:** additive optional fields need no migration (the card collection is schemaless), and REST matches the existing client idiom. Build gotcha (same family as the prod-build note below): the meteor app consumes `core-typings`/`rest-typings` as built `dist`, so new fields/endpoints require rebuilding those two packages before the app's `tsc` sees them.

### 2026-06-24 — Adversarially review my own Boards work before the checkpoint
**Chose:** run a multi-agent review (5 dimension reviewers → per-finding verification) over the feature diff before opening the PR, and fix every confirmed finding in a second commit.
**Why:** none of it is browser-verified (the Meteor stack is heavy to boot), so an automated adversarial pass is the strongest correctness gate available pre-merge. It found 11 real bugs — including the >100-card subtask cap and a Gantt drag listener leak — that typecheck and lint alone would never surface.

### 2026-06-24 — Org auto-provision: service provision-key + IMPORT accounts (not user-token + invite)
**Chose:** (1) MatterChat authenticates to CentralizedAuth's roster endpoint with a shared **provision key** (`x-provision-key`, or a KeyGate `auth:organizations:read` token) via a new `ProvisionApiAuthGuard` mirroring `EmailApiAuthGuard`. (2) On a firm admin's first OmnisAI login, MatterChat fetches the org roster (new `GET /organizations/:id/members`) and **pre-creates a linked MatterChat account per teammate** (`services.omnisai.id = sub`); their later sign-in adopts the doc.
**Rejected:** (1) reusing the admin's OIDC access token as a Bearer to the org endpoints — CentralizedAuth's `AuthGuard` is session-cookie based (no `bearer` plugin) and rejects it (LitBox only works because it validates the JWT via JWKS; auth's own endpoints don't). (2) `invite-multiple` — the firm's team are **already** the org's `organization_users`, so it rejects every one as "already a member" (0 invited), and it would need SMTP (staging has none).
**Why:** the design assumed the existing bulk-invite + user token would "just work"; investigation showed neither does. The provision-key is the same server-to-server model CasePro uses with `CRM_API_KEY` (founder-approved); pre-create is what actually delivers "the whole team is just there," and works without email. Additive on both sides → low blast radius. PRs: MatterChat #11, CentralizedAuth #352.

### 2026-06-24 — Cross-firm went LIVE via a verified-identity proxy, hardened after a red-team
**Chose:** route the browser → CFCS through the MatterChat `/_crossfirm` server proxy that injects the server-verified OmnisAI subject as an unforgeable `x-cfcs-caller`; run CFCS in STRICT mode where a single pre-dispatch identity gateway binds every actor field to the resolved caller (unique-or-fail-closed) and the service refuses to start without a real `CFCS_AUDIT_KEY`.

### 2026-06-25 — OIDC signature: better-auth signs id_token HS256 by default — alg-aware verify; strict-enable gated
**Root cause (diagnosed + reproduced):** the "signature did not verify (fail-soft)" warning was not a JWS encoding subtlety — better-auth signs the OIDC `id_token` with **HS256** (HMAC over the app secret) **by default**, NOT with the Ed25519 / OKP key published in the JWKS. The old verifier always took the JWKS path and checked an HMAC signature against the OKP public key, which can only ever return false. So the signature check was effectively dead (fail-soft), and only iss/aud/exp guarded the token.
**Chose:** make `verifyOmnisaiIdToken` **alg-aware**, branching on the JOSE header `alg` (`app/omnisai-oauth/server/verifyIdToken.ts`):
- `HS256` → recompute `HMAC-SHA256(clientSecret, signingInput)` and compare constant-time (`verifyHs256`, length-guarded `timingSafeEqual`), skipping the JWKS entirely. If `OmnisAI_OIDC_Client_Secret` is configured we **throw** `id_token_bad_signature_hs256` on mismatch (strict); if it is empty we keep the historical **fail-soft** (warn + continue).
- `EdDSA` / `RS256` / absent → the existing JWKS path, **kept fail-soft** (not flipped to throw) until a live EdDSA token is confirmed end-to-end.
- `none` → **rejected** outright (`id_token_alg_none_rejected`); an unsigned token is never acceptable.
**Additive / no live-behavior change:** with no secret configured (the live state), every path stays fail-soft exactly as before. The new `OmnisAI_OIDC_Client_Secret` setting (server-only, `secret: true`, empty default) and the `OMNISAI_OIDC_CLIENT_SECRET` env fallback are the only switches that turn on enforcement.
**To actually enforce a strict signature, pick ONE:**
- **Set `OmnisAI_OIDC_Client_Secret`** to the better-auth app secret and verify against a **live token** end-to-end first (the HS256 secret is the issuer's app secret; once set, a bad signature fails the login closed); OR
- **Route A — `useJWTPlugin: true`** in CentralizedAuthBackend so the issuer signs the id_token with **EdDSA** (the published JWKS key); then the JWKS path can be flipped from fail-soft to throw.
**Note:** strict **iss / aud / nonce** enforcement is a *separate* gap — it needs CentralizedAuth to actually **emit** those claims (the current MCP id_token omits iss/aud and does not echo the nonce); until then those stay accept-when-absent / non-fatal as documented above.
**Rejected:** flipping the existing JWKS verify to throw (it would block every live login, since the live token is HS256, not EdDSA — the JWKS path never sees a verifiable signature today).

### 2026-07-24 — chi.session-exchange verifies HARD on both lanes; never inherits verifyIdToken's fail-soft
**Chose:** the standalone-Chi auth bridge (`POST /v1/chi.session-exchange`) fails CLOSED on every check, split into two lanes: (a) asymmetric JWTs (EdDSA/RS256/ES256) verify against the issuer JWKS with `iss` REQUIRED (origin match) and `aud`-when-present required to hit the `Chi_Session_Exchange_Client_Ids` allowlist (empty allowlist + present aud = reject, with a distinct reason so the admin knows to configure it); (b) HS*-signed or opaque tokens go to live introspection at the issuer's `get-session` over TLS — we never hold the issuer's HMAC secret, because a workspace holding it could mint arbitrary identities. `alg:none` is terminal; a signature that verifies but yields bad claims never falls through to introspection. Identity mapping REUSES the web login's (exported `resolveOmnisaiUser`), so desktop and web land on the same account; the minted token mirrors `users.createToken` internals (hashed resume token — REST auth only matches `hashedToken`; loginHandler's raw-push works only because Meteor's resume path migrates legacy tokens) with `when` BACKDATED so the stock expiry sweep retires it in ~30 days instead of forking the expiry mechanism.
**Rejected:** copying verifyIdToken's accept-when-absent iss / warn-and-continue signature posture — that token arrives over OUR back-channel TLS call bound to state+PKCE, this one arrives from an unauthenticated public client and is attacker-suppliable; also rejected requiring the JWT lane only (better-auth's default tokens are HS256/opaque — the bridge would never work against the live issuer without the introspection lane).
**Chi-Desktop side:** PKCE public client (no secret ever), system browser only, `chi://` protocol return + fixed-port loopback fallback (DCR redirect_uris are exact-match ⇒ port must be stable), safeStorage-only token vault in the MAIN process, refresh-token rotation. DCR is self-serve on CentralizedAuth; if closed, the app logs the exact registration JSON instead of dying.
**Not live-verified:** `auth-app.omnisai.io` (and the auth.omnisai.io login page) time out from the dev Mac — the OAuth leg + happy-path exchange need a network that reaches auth; the endpoint gate/verification paths are unit-tested (25 specs) and the disabled-gate response is verified on staging post-deploy.

### 2026-07-30 — Org provisioning goes per-ORG: marker collection as the lock, org-admin claim as the trigger, firmId stamped on every login
**Chose:** (1) a dedicated raw collection `matterchat_org_provisions` (via the app-tree `db` handle, mirroring web-push subscriptions — NO @rocket.chat/models class, so no packages/model-typings edit and no turbo-rebuild gotcha) with `_id` = the CentralizedAuth orgId; the built-in `_id` unique index IS the concurrency lock — the claim is one `$or:[failed, stale-pending]`-filtered upsert, and a duplicate-key E11000 means the claim was lost ('done' or a fresh run in flight). 'failed' and stale-'pending' (>10 min) re-arm on the next qualifying login; forcing a re-run = ops deletes the marker doc (the import dedups by sub/email, so re-runs are always safe). (2) Trigger = workspace admin OR org-admin per the `casepro:role` claim matched against env `MATTERCHAT_ORG_ADMIN_ROLES` (default `admin,owner`, case-insensitive — env not a setting, matching the MATTERCHAT_PROVISION_KEY standalone pattern) — the old workspace-admin-only gate structurally dead-ended every org after #1. (3) `customFields.firmId` (the exact field PR #166's scoping reads) stamped from the org claim on EVERY login inside `resolveOmnisaiUser` (covers web OIDC + Chi session-exchange), on roster import, and by a startup backfill applier (`orgBackfill.ts`) for pre-existing OIDC users; stamp is a `$exists:false`-guarded atomic update + `firmIdSource:'omnisai'` — a DIFFERENT existing firmId (self-serve Team _id, or an org move) is warn-logged and KEPT, never overwritten. The applier also seeds 'done' markers from the legacy per-admin `services.omnisai.provisionedOrgId` field so the first deploy never re-provisions org #1; that legacy field is no longer written.
**Rejected:** (a) a registered @rocket.chat/models class for the marker (drags in packages + the prod-build stale-dist gotcha for a 4-field bookkeeping doc); (b) trusting `casepro:role` literals in code (the fork treats the claim as opaque; vocabulary unverified against CentralizedAuth — hence the env override, and workspace-admin stays an OR-gate so org #1 keeps working regardless); (c) auto re-stamping firmId on an org-claim change (silent re-cohorting a user who may be mid-conversation in their firm; org moves are an explicit ops action); (d) a vNNN migration for the backfill (an every-boot applier with a self-guarding query also catches users linked by any straggler old-code pod, and avoids the parallel-workstream migration-number collisions).
**Known trade-offs:** OIDC-stamped users get an org UUID in `customFields.firmId`, so `getFirmForUser`'s `Team.getOneById(firmId)` → null and the self-serve "My Firm" panel/invites are inert for them (scoping itself only needs equality — works fine); the Chi introspection lane can resolve a session with no org claims → no stamp until that user's next web login; enabling `Firms_Scoped_Directory` on prod AFTER the backfill flips previously-mutually-visible OIDC users into per-org cohorts in one shot (intended isolation — founder should expect the directory change).
### 2026-07-30 — Firm invite links are always finite: settings-driven caps + boot sweep of pre-existing unlimited links
**Chose:** two server-only int settings in the OmnisAI group — `Firms_Invite_MaxUses` (default 25) and `Firms_Invite_Expiry_Days` (default 7) — resolved through a pure helper (`resolveFirmInviteLimits` in `server/lib/firms/firmsHelpers.ts`) that snaps any admin value to the value sets stock `findOrCreateInvite` accepts (days [1,7,15,30], uses [1,5,10,25,50,100]) and deliberately EXCLUDES 0, so neither "unlimited uses" nor "never expires" can come back through configuration (0/negative snaps UP to the smallest allowed value; garbage falls back to the defaults). Creation (`inviteToFirm`) reads the settings per call and the invite email states the real limits. Redemption enforcement is stock Rocket.Chat and already complete — `validateInviteToken` rejects expired (`expires <= now`) and exhausted (`maxUses > 0 && uses >= maxUses`) invites, `useInviteToken` calls it before joining and only counts first-time joiners, and `registerUser` gates registration through the same check in Secret-URL mode — so the hardening is creation-side plus retro data. Already-issued unlimited invites (prod has `Firms_SelfServe_Enabled` on, links may be circulating): a boot-time idempotent sweep (`server/omnis/config/tightenFirmInvites.ts`, the PR #171 applier pattern) caps every `maxUses: 0` invite on a `firmTeam` room at the configured cap; their 15-day expiry is left as-is since it was always finite. Default rationale: 25 uses matches `MAX_INVITES_PER_CALL` (one link serves a full email batch); 7 days is the nearest STOCK-VALID value to the proposed 3 — supporting 3 would require editing stock `findOrCreateInvite`'s `possibleDays` list (a core-file edit the mergeability rule discourages).
**Rejected:** (a) adding 3 to `possibleDays` — a marked core edit plus error-string churn for marginal gain over 7 days; revisit only if the founder insists on 3; (b) letting old unlimited invites age out on their own 15-day expiry — the sweep is one idempotent `updateMany` and closes the window now; (c) rejecting out-of-range setting values with errors — snapping keeps `firms.invite` working under any admin input, and the setting descriptions state the allowed values; (d) renaming the exhausted-uses error — stock deliberately reports exhausted links as `error-invite-expired`, and reusing it keeps the existing InvitePage dead-link UX (`Invalid_or_expired_invite_token`) untouched.
**Known consequences:** an old link whose `uses` already exceeds the new cap goes dead immediately (reads as "expired" to the visitor); the next `firms.invite` call auto-mints a fresh link because `findOrCreateInvite`'s dedupe query skips exhausted/expired documents — no regenerate UI needed. Staging QA still needs `Firms_SelfServe_Enabled` flipped on (off there per the 2026-07-30 audit). In `Accounts_RegistrationForm='Public'` mode a dead invite still allows bare registration (stock behavior — the visitor lands firm-less in the create-a-firm onboarding); caps make that path slightly more common, accepted for now.
