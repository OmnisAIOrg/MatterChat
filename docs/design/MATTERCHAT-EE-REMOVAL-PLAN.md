# MatterChat — removing Rocket.Chat EE code (plan)

Generated 2026-07-30 by a 7-agent audit (5 mappers + planner + adversarial critic).
Goal: run as pure MIT — no license machinery, no air-gapped countdown, no seat caps.

> **Critic verdict:** NOT safe to execute as written — see Blockers. Fix those first.

## Strategy

Neutralize first, delete last — do NOT run `scripts/fossify.ts` and do NOT start with `rm -rf ee/`. The audits agree on the shape of the problem: the EE tree is 95% additive (patch-injection middleware, `License.onLicense` listeners, extra core-services, extra settings groups) and falls away harmlessly, but four things are load-bearing for MIT code and must be re-provided in MIT before anything is deleted — `IReadReceiptsArchiveModel` (registered only at apps/meteor/ee/server/models/startup.ts:10, and `packages/models/src/proxify.ts:19` THROWS on an unregistered model), the Meteor→Presence connection wiring (apps/meteor/ee/server/startup/presence.ts, the only thing that ever marks a user online), the Apps-Engine orchestrator (`registerOrchestrator` is called only at apps/meteor/ee/server/apps/orchestrator.js:402), and the nine EE workspace packages under ee/packages/ that MIT core imports directly. Stage the work as: (1) add MIT replacements additively without wiring them, (2) flip the two boot imports (apps/meteor/server/main.ts:15 and apps/meteor/startRocketChat.ts:1-3) so the ee tree stops being evaluated at all — at that moment the air-gapped countdown is already dead because apps/meteor/app/license/server/airGappedRestrictionsWrapper.ts:3-5 is already a pass-through and only the EE patch ever threw `restricted-workspace` — then verify boot and message send/update, (3) swap `@rocket.chat/license` for a drop-in MIT package, (4) only then delete the trees, (5) clean build/CI config last. On the license question: build ONE MIT workspace package at `packages/license` that keeps the package NAME `@rocket.chat/license` (packages/ is MIT per LICENSE:5-12) rather than editing all 18 MIT call sites first. That single decision removes ~18 runtime edits, 5 test-mock edits, the client deep-import at apps/meteor/client/hooks/useLicenseLimitsByBehavior.ts:2, and the apps/meteor/package.json dependency edit, and — critically — it keeps two of the riskiest call sites (apps/meteor/app/api/server/ApiClass.ts, apps/meteor/app/api/server/lib/getServerInfo.ts) untouched while another process is editing apps/meteor/app/api/server/. Six call sites still need real edits afterwards because a false-returning stub changes their meaning, not just their value (omnichannel queue start, the usageReport countdown trigger, the contact-id-verification importer registration, workspaceUrl/hashedWorkspaceUrl, applyLicense in cloud registration, and the client `/v1/licenses.info` fetch) — those get explicit steps. Apps-Engine is a founder decision, not a code decision: the entire orchestrator is EE-licensed by path, upstream's own FOSS build drops it, and MIT core has only 7 non-optional `Apps.*` accesses (getAppsStatistics.ts:31, migrations v294.ts:13/15/16, v307.ts:20/22/23) — the default plan is to drop it and guard those 7 with `Apps.self?.`, because relicensing 296 EE files as MIT is not something an engineer may decide. Presence is the one genuinely large port: ~800 lines across ee/packages/presence/src/Presence.ts, lib/presenceEngine.ts and lib/PresenceReaper.ts must be clean-room reimplemented as MIT `packages/presence` against the MIT `IPresence` interface in packages/core-services/src/types/IPresence.ts, or every user stays permanently offline on a server that boots and looks healthy. Every step below is additive or confined to files we own, with `// MATTERCHAT:` markers on the unavoidable core edits (main.ts, startRocketChat.ts, ApiClass.ts, the 7 Apps guards, the 6 semantic license call sites).

## Blockers & problems found by the adversarial reviewer

### [BLOCKER] Step 3 creates an MIT workspace package named `@rocket.chat/presence` while `ee/packages/presence` (same name) is not deleted until step 12. Yarn 4 hard-errors on duplicate workspace names, so `yarn install` — and step 3's own verify command — fail, and every subsequent step is blocked.

- **Evidence:** ee/packages/presence/package.json:2 `"name": "@rocket.chat/presence"`. Root package.json:17-22 globs BOTH `"packages/*"` and `"ee/packages/*"`. package.json:190 `"packageManager": "yarn@4.12.0"`. Step 3 verify: `yarn workspace @rocket.chat/presence run build`; step 3 change text: "Leave apps/meteor/server/services/startup.ts:71 pointing at @rocket.chat/presence until step 12" — i.e. both packages coexist. Same latent hazard for packages/license vs ee/packages/license (ee/packages/license/package.json:2), mitigated only because step 6 does create+`git rm` in one step.
- **Fix:** Either (a) name the MIT package something non-colliding (e.g. `@matterchat/presence`) and repoint `apps/meteor/server/services/startup.ts:71` at step 12, or (b) move `git rm -r ee/packages/presence` INTO step 3 (safe: nothing imports it except services/startup.ts:71, which step 4c/step 3 can flip at the same time). Also add an explicit note to step 6 that no `yarn install` may run between creating packages/license and deleting ee/packages/license.
